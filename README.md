# Домашний ассистент

Telegram-бот для семьи: задачи с дедлайнами, импорт событий из календарей, многоступенчатые напоминания (за сутки → за 3 часа → за 30 минут → эскалация в общий чат).

Node 20+ / grammY / PostgreSQL. Разворачивается на Railway так же, как AdTracker.

---

## Что уже работает

- регистрация членов семьи (`/start`), группа + топики
- создание задач обычным текстом: `завтра в 18:30 забрать посылку @wife, напомни за сутки и за 2 часа`
- парсер: с `ANTHROPIC_API_KEY` — через Claude, без него — регексповый фолбэк (русский, покрывает бытовые фразы)
- напоминания как строки в БД + тикер раз в минуту с атомарным захватом (`FOR UPDATE SKIP LOCKED`)
- grace-окно: протухшие после даунтайма напоминания не отправляются
- кнопки под напоминанием: ✅ Готово / ⏰ +1 час / 📅 Завтра / 🗑 Удалить
- адресная доставка: тело напоминания — в личку исполнителю, в общий чат — короткий пинг «@исполнитель, глянь личку» (`GROUP_PING`)
- эскалация в общий чат через 30 минут после дедлайна, если задачу не закрыли
- утренний дайджест «план на сегодня»
- импорт `.ics`-календарей (Apple, Outlook, Google — с оговоркой ниже), включая повторяющиеся события, EXDATE и переопределения отдельных вхождений
- события, удалённые в календаре, автоматически снимаются вместе с их напоминаниями
- повторяющиеся задачи в самом боте: «каждый вторник в 20:00», «по будням», «каждое 29 число», «каждый предпоследний день месяца», «каждый первый понедельник месяца», «каждые 2 недели», «ежедневно» — команда `/recur`

## Чего пока нет (следующие шаги)

- Google Calendar через API + `syncToken` (сейчас только через секретную `.ics`-ссылку)
- обратная запись задач бота в общий Google-календарь
- CalDAV для iCloud

## Пошагово

### 1. Бот в Telegram

@BotFather → `/newbot` → забрать токен. Потом `/setprivacy` → **Disable**, иначе в группе бот не увидит обычные сообщения (нужно для формата `+задача`). Если пользуетесь топиками — включить в группе форум-режим.

### 2. База

Локально:

```bash
createdb family
export DATABASE_URL=postgresql://localhost:5432/family
```

На Railway — добавить Postgres-плагин, `DATABASE_URL` подставится сам.

### 3. Запуск

```bash
cp .env.example .env    # вписать TELEGRAM_BOT_TOKEN и DATABASE_URL
npm install
npm run migrate         # применит migrations/*.sql
npm start
```

Проверить парсер без БД и без Telegram:

```bash
npm run selftest
```

### 4. Подключить семью

1. Добавить бота в семейную группу, дать права на чтение сообщений.
2. В группе — `/start`. Бот запомнит `chat_id` (и топик, если писать внутри топика).
3. Каждому написать боту в личку `/start` — иначе бот не сможет писать напрямую и не будет знать `@username` для назначения задач.

### 5. Первая задача

В личке — просто текстом. В группе — с `+` в начале:

```
+в среду вечером записать ребёнка к врачу @wife, напомни за сутки и за 2 часа
```

Бот ответит карточкой с распознанной датой и списком запланированных напоминаний — сразу видно, правильно ли он понял.

### 6. Календари

```
/cal add https://calendar.google.com/calendar/ical/…/basic.ics Мой рабочий
/cal list
/sync
```

Где взять ссылку:

- **Google:** Настройки календаря → «Секретный адрес в формате iCal»
- **Apple/iCloud:** Календарь → общий доступ → публичный календарь (webcal-ссылку заменить на `https://`)
- **Outlook:** Настройки → Общие календари → Опубликовать → ICS

⚠️ У Google ICS-фид кэшируется на его стороне и обновляется с задержкой до нескольких часов. Для быстрой синхронизации нужен переход на Google Calendar API — это следующий шаг, см. ниже.

### 7. Деплой на Railway

Вариант A — отдельный проект. Переменные из `.env.example`, старт `npm start`.

Вариант B — отдельный **сервис** внутри существующего проекта, из той же репы (Root Directory `/family-bot`), с той же Postgres, но своей схемой (`DB_SCHEMA=family`). Так дешевле и меньше сущностей. Подробности и подводные камни — в разделе «Подселение к существующему проекту» ниже.

Порт открывается healthcheck-сервером, Railway этого достаточно.

## Подселение к существующему проекту

Бот умеет жить в одной базе с другим приложением: все его таблицы лежат в отдельной схеме (`DB_SCHEMA`, по умолчанию `family`), `search_path` выставляется на этапе установки соединения.

Это не косметика. Имена `users`, `tasks`, `settings`, `_migrations` слишком общие — при работе в `public` рядом с другим приложением `create table if not exists users` **молча ничего не создаст**, и бот начнёт писать в чужую таблицу пользователей. Схема закрывает вопрос полностью.

Проверить, что не пересеклись:

```sql
select table_schema, table_name
  from information_schema.tables
 where table_name in ('users','tasks','settings','reminders','calendars','_migrations')
 order by 1,2;
```

Бэкап только своей схемы:

```bash
pg_dump "$DATABASE_URL" --schema=family -Fc -f family.dump
```

Отдельный сервис против «в том же процессе»: держите бота отдельным процессом. Общий процесс означает, что необработанный промис в семейном боте роняет основное приложение, а деплой семейной фичи перезапускает его фоновые джобы.

## Устройство

```
src/
  index.js          точка входа: миграции, бот, хартбиты, /health
  db.js             пул, миграции, settings-хелперы
  time.js           таймзоны, офсеты, человекочитаемые формулировки
  parser.js         текст → {title, dueAt, offsets, assignee}
  recurrence.js     разбор «каждый вторник», RRULE, материализация вхождений
  reminders.js      генерация, диспетчер, done/snooze
  bot.js            команды, кнопки, дайджест
  calendar/ics.js   импорт и разворачивание повторяющихся событий
migrations/001_init.sql
```

Три фоновых цикла, все — короткие `setInterval`-хартбиты с флагом `running` (длинные `setTimeout` теряются при засыпании контейнера):

| цикл | период | что делает |
|---|---|---|
| reminders | 60 с | забирает созревшие напоминания и отправляет |
| calendars | 15 мин | тянет `.ics`, апсертит события |
| recurrences | 1 час | достраивает задачи по повторяющимся правилам на горизонт вперёд |
| digest | 60 с | раз в сутки в 8:00 шлёт план на день |

### Почему напоминания — строки в таблице

`setTimeout` живёт в памяти процесса и умирает при каждом деплое. Строка с `fire_at` переживает всё. Диспетчер забирает пачку одним `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)` — два инстанса не отправят одно и то же дважды.

### Пересборка при изменении срока

При смене `due_at` удаляются только `pending`-напоминания, `sent` остаются. Импорт из календаря сравнивает отпечаток события (`etag = summary|start|location`) и трогает напоминания только если событие реально изменилось — иначе каждый пулл сбрасывал бы «уже отправлено».

### Задачи без времени

Для `all-day` дедлайн ставится не на 00:00, а на `ALL_DAY_HOUR` (по умолчанию 9 утра). Иначе «напомнить за сутки» прилетает в полночь.

## Что делать дальше (Google Calendar API)

1. Google Cloud → проект → включить Calendar API → OAuth-клиент типа Desktop.
2. Одноразовый скрипт: выдать ссылку на consent, обменять код на `refresh_token`, положить в `calendars` (добавить колонки `refresh_token`, `sync_token`, `google_calendar_id`).
3. Пулл раз в 5 минут: `events.list({ calendarId, syncToken, singleEvents: true, showDeleted: true })` — Google сам разворачивает повторения, RRULE руками разворачивать не нужно.
4. `status === 'cancelled'` → снять задачу и погасить напоминания (логика уже есть в `ics.js`, переиспользуется).
5. `410 Gone` на `syncToken` → сделать полный ресинк с нуля.

Push-уведомления (`events.watch`) тоже возможны, но канал живёт максимум 7 дней и требует перерегистрации — пулл с `syncToken` проще и для семьи достаточно.
